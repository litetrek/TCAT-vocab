## 背景與設計決策（已與設計者確認）

1. **Anthropic 沒有原生 embedding API**，本專案目前只裝了 `anthropic` 套件，沒有任何 embedding 供應商
2. **決策：兩家都接，先並行比較，之後再選一家**——不是一次押寶。原設計指南的 `trans_revisions.embedding vector(1536)` 單一欄位方案作廢，改成兩個獨立欄位：`embedding_voyage vector(1024)`（Voyage AI `voyage-3`）與 `embedding_openai vector(1536)`（OpenAI `text-embedding-3-small`）
3. **兩把金鑰都設為選填**：任一把 `.env` 沒設定，該供應商的 embedding 就跳過（存 NULL），不可讓主流程（翻譯/儲存修訂）因為 embedding 失敗而整個報錯中斷——比照 `translate_unit()`／`group_sentences_by_topic()` 的容錯模式
4. **檢索時只用一家**：由 `.env` 的 `EMBEDDING_PROVIDER`（預設 `voyage`）決定翻譯時 RAG 範例檢索用哪一欄；寫入修訂時仍兩欄都嘗試寫入，供之後離線比較
5. 新增一支比較腳本，讓你能人工判斷哪家retrieval 品質較好，決定好後再考慮把另一欄的程式碼與欄位清掉（本階段不做清除，先求可比較）

## 任務三：Migration 008 — 雙欄位 + 檢索用 RPC

新增 `migrations/008_dual_embeddings.sql`：

```sql
alter table trans_revisions drop column if exists embedding;
alter table trans_revisions add column if not exists embedding_voyage vector(1024);
alter table trans_revisions add column if not exists embedding_openai vector(1536);

create or replace function find_similar_revisions_voyage(query_embedding vector(1024), match_limit int default 5)
returns table(id bigint, display_id text, chinese_text text, english_after text, similarity float)
language sql stable as $$
  select id, display_id, chinese_text, english_after,
         1 - (embedding_voyage <=> query_embedding) as similarity
  from trans_revisions
  where embedding_voyage is not null
  order by embedding_voyage <=> query_embedding
  limit match_limit;
$$;

create or replace function find_similar_revisions_openai(query_embedding vector(1536), match_limit int default 5)
returns table(id bigint, display_id text, chinese_text text, english_after text, similarity float)
language sql stable as $$
  select id, display_id, chinese_text, english_after,
         1 - (embedding_openai <=> query_embedding) as similarity
  from trans_revisions
  where embedding_openai is not null
  order by embedding_openai <=> query_embedding
  limit match_limit;
$$;
```

- 建立 `scripts/run_migration_008.py`（比照 `run_migration_007.py` 的結構）：套用遷移 + 驗收測試（插入一筆測試 revision、寫入兩欄假向量、呼叫兩個 RPC 都能查到、清理測試資料）
- 語料量小（目前 `trans_revisions` 應該還是空的或極少），**不建 ivfflat/hnsw 索引**，比照設計指南「語料 < 數萬筆不需要建索引」原則，全表掃描已足夠快

## 任務五：RAG 檢索注入翻譯 Prompt

### `ai.py` — `translate_unit()` 再加一個選填參數
- 新增 `similar_examples: list = None`，格式 `[{"chinese": str, "english": str, "similarity": float}, ...]`
- 若非空，組裝一段 few-shot 範例區塊，插入在 style guide 之後、術語約束之前（對齊設計指南第六部分順序：風格指南 → 術語約束 → 相似範例 → 待譯句）：
  ```
  \nSimilar past translations (for tone/style reference only — do not copy verbatim unless the source text is identical):
  中文: ... → English: ...
  中文: ... → English: ...
  ```
- 相似度門檻：呼叫端（見任務六）負責過濾，`translate_unit()` 本身不做門檻判斷，收到什麼就用什麼

### 任務六：`routes/translate.py` — `api_translate_unit()` 串接檢索
- 在呼叫 `translate_unit()` 前：
  1. 讀 `EMBEDDING_PROVIDER` env var（預設 `voyage`）
  2. 呼叫對應的 `embeddings.get_voyage_embedding()` 或 `get_openai_embedding()` 取得該 unit `chinese_text` 的 query embedding；拿不到（`None`）就跳過整個 RAG 步驟，`similar_examples` 傳 `None`
  3. 呼叫對應的 `find_similar_revisions_voyage` 或 `find_similar_revisions_openai` RPC，`match_limit=5`
  4. **相似度門檻**（冷啟動保護，對齊設計指南第六部分）：`similarity < 0.5` 的結果一律捨棄；全部被捨棄則 `similar_examples` 傳 `None`（不注入，避免用不相關的範例誤導）
  5. 這整段查詢失敗（RPC 錯誤等）一樣要容錯，不可讓翻譯請求失敗

### 驗收標準（任務五、六）
- `trans_revisions` 累積至少 2-3 筆有 embedding 的資料後，對一句語意相近的新句子呼叫翻譯端點，確認有查到相似範例並注入 prompt（可從函式呼叫參數或加一行除錯輸出確認，不需要真的驗證 AI 有沒有「參考」到）
- 語料還很少、相似度都低於門檻時，確認翻譯請求正常完成、不注入範例、不報錯
