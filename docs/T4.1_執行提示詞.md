## 背景

- `style_guide` 表已存在（`migrations/005_t1_translation_module.sql`），欄位：`id, display_id(S000001), category, rule_text, example_before, example_after, active, source_revision_ids, created_by, created_at`
- `category` 只能是：`honorifics` / `proper_nouns` / `sentence_splitting` / `tone` / `other`
- **本階段不需要新的 migration**
- `translate_unit()`（`ai.py`）目前的 prompt 組裝順序：角色說明 → 術語約束（`term_hint`）→ 前後句上下文（`context_hint`）→ 長句拆分要求（`split_hint`）→ 待譯句。本階段要在「角色說明」之後、「術語約束」之前插入「風格指南」區塊，對齊設計指南第六部分的順序。
- 沿用專案既有慣例：`routes/translate.py` 對 `trans_*` 系列表格直接呼叫 `supabase.table(...)`，沒有獨立 repository 檔（不同於 `terms_repo.py` 這種舊系統表）。本階段比照辦理，不新增 `style_guide_repo.py`。
- 權限：查看規則列表 member+ 皆可（用來理解目前風格指南在管什麼）；新增/停用/編輯規則僅 leader+（`is_leader()`，已在 `auth.py` 存在，`routes/translate.py` 已 import）。

## 任務一：API 端點（`routes/translate.py`）

新增於檔案內獨立區塊 `# ── T4.1 — Style Guide ──`：

### `GET /api/trans/styleguide`
- 權限：`_require_translation`（member+ 可查看，含 inactive，讓 leader 管理畫面能看到全部）
- 回傳全部規則，依 `category, created_at` 排序

### `POST /api/trans/styleguide`
- 權限：`_require_translation` + `is_leader()`（不符回 403 "Leader role or higher required"）
- 輸入 JSON：`category`（必填，需在允許值內，否則 400）、`rule_text`（必填）、`example_before`、`example_after`（皆選填）
- `display_id` 用 `next_display_id` RPC，`p_prefix="S"`, `p_seq_name="seq_style_guide_display"`
- `created_by` = `session["user_email"]`，`active` 預設 `true`
- 回傳新建列（201）

### `PATCH /api/trans/styleguide/<id>`
- 權限：`_require_translation` + `is_leader()`
- 輸入 JSON 可包含：`category`、`rule_text`、`example_before`、`example_after`、`active`（布林，用來停用/重新啟用；**不做硬刪除**，比照設計指南「停用不刪除」）
- 只更新有傳入的欄位；找不到該筆回 404
- 回傳更新後的列

**不要求**寫 `audit_log`（style_guide 目前不在既有審計機制覆蓋範圍內，之後有需要再補，先求端點可用）。

### 驗收標準（任務一）
- 以 leader 帳號 POST 一筆規則、GET 列表看得到、PATCH 停用後 `active=false`、再 PATCH 啟用回 `true`
- 以 member（非 leader）帳號 POST/PATCH，皆收到 403；GET 仍可成功
- `category` 傳入不在允許清單的值，收到 400

## 任務二：Prompt 注入（`ai.py` — `translate_unit()`）

- 新增選填參數 `style_rules: list = None`，格式 `[{"category": str, "rule_text": str}, ...]`（`example_before`/`example_after` 若有值也可傳入，用於 few-shot 提示，但非必要）
- 若 `style_rules` 非空，組裝一段 `style_hint`，插入在現有 `term_hint` **之前**：
  ```
  \nStyle guide — house rules to follow:\n- [category] rule_text\n- [category] rule_text ...
  ```
  若某規則有 `example_before`/`example_after`，可附加 `(e.g. "example_before" → "example_after")` 在該行後面
- 不改變函式既有的容錯行為（任何解析錯誤仍回傳 `fallback`，不可拋錯中斷）

### 驗收標準（任務二）
- 呼叫 `translate_unit(..., style_rules=[{"category":"tone","rule_text":"避免使用第一人稱「我」，改用「筆者」或改寫句式"}])`，確認組裝出的 prompt 字串含有該規則文字（可用簡單的單元測試或印出 prompt 內容檢查，不需要真的呼叫 API）

## 任務三：串接（`routes/translate.py` — `api_translate_unit()`）

- 在呼叫 `translate_unit(...)` 前，新增一步：查詢 `style_guide` 表 `where active = true`，取出 `category, rule_text, example_before, example_after`
- 查詢失敗（例如資料庫暫時錯誤）時：**不可讓整個翻譯請求失敗**，比照 `_match_constraint_terms()` 的容錯寫法（`try/except` 回傳空列表）
- 將結果傳入 `translate_unit(..., style_rules=active_rules)`

### 驗收標準（任務三）
- 新增至少一筆 active 規則後，對一個真實 unit 呼叫 `POST /api/trans/units/<id>/translate`，確認翻譯結果有反映風格指南（例如規則要求避免某用詞，實際輸出未出現該用詞——可能需要多試幾次，AI 遵從度非 100% 屬預期）
- 停用該規則（`active=false`）後重新呼叫，確認端點仍正常運作（不會因為沒有規則而出錯）

### 驗收標標準（任務四）
